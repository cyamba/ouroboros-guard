# Prediction card

Fill this in **before** looking at outcomes, commit it (`oguard commit prediction_card.md`), and publish the
`.commit.json`. It fixes what you are predicting and how you will be judged, so neither can drift later.

| Field | Entry |
|-------|-------|
| Study / project | |
| Author(s) and agents | (people, models and versions) |
| Prediction time (`as_of`) | |
| Targets | (what is predicted, one line each, or the file that lists them) |
| Outcome definition | (exactly how the outcome will be measured; who measures it) |
| Outcome source and expected date | |
| Inputs allowed | (registered inputs, with availability dates) |
| Tools allowed | (search, databases, code; with as-of dates and blocked sources) |
| Primary metric | (and the threshold for calling the prediction a success) |
| Chance level / baseline | |
| Replicate ceiling | (replicate agreement or test-retest correlation, if known) |
| Negative controls planned | (scrambled labels, masked identities, temporal split) |
| What would change our mind | (the result that would count against the method) |
| Known risks of leakage | (and how each is handled) |
